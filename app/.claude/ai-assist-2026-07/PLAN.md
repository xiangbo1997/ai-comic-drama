## 1. 背景与痛点

用户（非专业漫剧制作者）在使用工作台时的七个痛点：

| #   | 痛点                                         | 类型         |
| --- | -------------------------------------------- | ------------ |
| 1   | 没有剧情描写与分析能力                       | 输入能力缺失 |
| 2   | 没有人物刻画和描述能力                       | 输入能力缺失 |
| 3   | 没有把控全场的能力                           | 决策能力缺失 |
| 4   | 每一步都要去另一个 AI 界面问答再复制粘贴回来 | 工作流断裂   |
| 5   | 生成的角色不是想要的                         | 产出质量     |
| 6   | 生成的图片不是想要的                         | 产出质量     |
| 7   | 生成的视频连贯不起来                         | 产出质量     |

## 2. 根因分析（结论收录）

七个痛点收敛为两个根因，且互为上下游：

### 根因一：期望对齐缺失（痛点 1/2/4/5/6 的共同根源）

系统的一致性机器已经很强（统一编排器：策略选择→参考图注入→人脸验证→seed 重试；
多角色合成参考图；三视图；自动 workflow 内 Observer 质检+反思闭环），
「生成忠实于输入」这一半没有大问题。断裂发生在生成之前：

1. 用户写不出角色描述/世界观 → 输入模糊；
2. 定妆照基于模糊描述生成 → 锚本身就不是用户想要的形象；
3. 后续全链路一致性锚定这张定妆照（canonicalImageUrl/三视图/人脸验证）
   → 系统越忠实，越忠实地复制一个错的锚；
4. 单发抽卡（每次只出 1 张）→ 用户没有挑选空间，重抽又回到「不会写 prompt」死循环。

### 根因二：视频连贯机制存在，但全是「局部的、要手动开的」（痛点 7）

| 层次          | 已有机制                                             | 缺口                                 |
| ------------- | ---------------------------------------------------- | ------------------------------------ |
| 单分镜内部    | 时长拆段+末帧链式衔接+ffmpeg 拼接（video-segmenter） | 基本完整                             |
| 相邻分镜·视觉 | `videoLinkNext` 尾帧衔接（FL 首尾帧插值）            | 默认关、每镜手动开、要求下一镜已出图 |
| 相邻分镜·叙事 | video-director 拿 prev/next 描述做上下文             | 仅文本层承接                         |
| 全片          | xfade 转场、色板门禁、故事圣经                       | 转场掩盖不了内容跳变                 |

**核心结论**：视频连贯性的根源在图片层——每镜图独立生成，镜头间唯一共享锚是角色参考图，
**场景/环境没有锚**（同一房间在不同镜头可能完全不同）。视频是 I2V，图不连贯则视频必然不连贯。
对照动画工业的连续性管理三要素：角色设定稿（✅已有）、场景设定稿（❌缺失）、
场记连续性检查（❌仅文本层，无视觉层校验）。

## 3. 决策记录

| 决策点       | 结论                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------- |
| 实施顺序     | 严格按 阶段一 → 二 → 三；2.1（轻量连贯）允许与阶段一并行                                              |
| 抽卡成本     | 做成用户可选档位 1/2/4 张，默认 1（成本不变）；按张扣费、失败张退款                                   |

## 4. 阶段一 · 期望对齐层（P0）

> 目标：把「空白页恐惧」消掉——用户从「自己写」变成「改 AI 写的」；
> 把「抽一张赌一张」变成「抽 N 张挑一张」。全阶段以文本 LLM 调用为主，成本低。

### 1.1 世界观 / 主角 AI 起草

- **现状**：`DramaScriptInput.worldview` 必填且纯手写（`types/drama.ts`）；
  `DramaScriptAgent` 已有「世界观→结构化脚本」能力，但入口卡在用户写不出世界观。
- **改动范围**：
  - 新增 API 路由（如 `POST /api/drama/draft-worldview`，命名对齐现有 drama 路由风格）：
    输入一句话想法（+可选题材/系列上下文）→ 输出 `{ worldview, protagonist, genre, filmTitle }`。
  - 服务端复用 Agent 骨架（Zod 校验 + parseLooseJSON + 修复重试，参照 `drama-script-agent.ts`）；
    prompt 融合已有爆款方法论层。
  - 前端：世界观表单加「AI 起草」按钮，结果填入可编辑字段。
- **实现要点**：起草不覆盖已有非空字段（或弹确认）；系列续集时注入前情（`lib/series.ts` 已有摘要能力）。
- **验收标准**：
  - 一句话输入（如「重生复仇爽剧，女主是被陷害的豪门千金」）→ 四字段填充且可编辑；
  - 3 种不同题材手测均产出合格世界观；
  - `pnpm ci` 全绿。
- **工作量**：S

### 1.2 角色描述 + 外貌 10 字段 AI 预填

- **现状**：
  - 外貌编辑器（`components/appearance-editor.tsx`）10 字段（发型/发色/脸型/瞳色/体型/身高/肤色/配饰/自由文本/服装预设）纯手填——用户复制粘贴最频繁的环节；
  - 「描述→结构化外貌 JSON」的 prompt **已存在**：`buildCompactAppearancePrompt`（`services/agents/character-bible-agent.ts` 内私有函数），只在自动 workflow 用；
  - 角色文字描述已有 AI 生成按钮（`generateDescriptionMutation`，输入姓名/性别/年龄）。
- **改动范围**：
  - 把 compact appearance prompt 抽到共享位置（`lib/prompts/` 下），`CharacterBibleAgent` 与新路由共用；
  - 新增 API（如 `POST /api/characters/appearance-draft`）：输入 name/gender/age/description
    （+可选参考图 URL）→ 输出 `AppearanceFormData` 形状 JSON；
  - 前端 `appearance-editor.tsx` 加「✨ AI 分析填写」按钮：只填空字段，非空字段不覆盖
    （提供显式「全部重填」二次确认入口）。
- **实现要点**：
  - **字段语言适配**（实现时必须核对）：表单下拉预设为中文（`HAIR_STYLES` 等），
    而 compact prompt 现输出英文——预填结果需与 UI 预设语言一致，同时不破坏出图侧 prompt 拼接；
  - 有参考图的角色：若用户 LLM 配置支持视觉输入，则走「看图反推外貌」（更准）；
    不支持则降级纯文本推断（不阻断）。
- **验收标准**：
  - 只有 description 的角色一键填出 10 字段，字段值与下拉预设兼容；
  - 用户已手填的字段在再次点击 AI 填写时保持不变；
  - `pnpm ci` 全绿。
- **工作量**：M

### 1.3 提示词 AI 建议

- **现状**：生成参考图弹窗（`GenerateReferenceModal.tsx`）的 customPrompt、
  分镜迭代生成的 note（`use-generation-actions.ts` iterate/note 机制）均为纯手填。
- **改动范围**：
  - 两处输入框加「帮我写」按钮：基于角色信息/分镜上下文（+当前图，视觉可用时）
    生成 2~3 条候选短句，点选填入后仍可编辑；
  - 服务端一条轻量 LLM 路由即可（可与 1.2 合并为一个 assist 路由族）。
- **验收标准**：建议可点选填入；空上下文时按钮禁用并提示。
- **工作量**：S

### 1.4 多候选抽卡 + VLM 择优 ⭐ 本阶段核心

- **现状**：
  - 角色定妆照与分镜图均为单发生成；
  - 版本历史基建已有：分镜域 `SceneVersion`/`GenerationAttempt`（`SceneVersionStrip` UI）、
    角色域 `GenerationAttempt`；
  - 图像生成已 task 化（POST 202 + taskId 轮询）；
  - Observer 图像评审（语义/情绪/景别/色调维度打分）已存在于 workflow，可复用为 VLM 择优打分器。
- **改动范围**：
  - **服务端**：`/api/generate/image` 与角色 generate-reference 路由支持 `count` 参数（1/2/4）：
    - `Promise.allSettled` 并行生成 N 张，每张落 `GenerationAttempt`；
    - 部分失败不整单失败；失败张走 `lib/credits.ts` 的 `refundCredits` 自动退款（扣费收口铁律）;
    - 生成后对每张跑 Observer 打分（用户 LLM 支持视觉时），标注 `recommended`；
      不支持视觉则只出图不打分（降级不阻断）；
  - **前端**：候选画廊（2×2 栅格），显示分数徽章与推荐标记，点选定稿
    （写 `isCurrent` / 角色 `referenceImages`）；与现有版本历史条带（SceneVersionStrip）融合；
  - **成本预览**：沿用「余额前置显示」模式（GenerateReferenceModal 已有），
    预览成本 = 单价 × N，档位切换实时刷新。
- **验收标准**：
  - 4 张档一次生成、画廊点选定稿生效；
  - 模拟单张失败：其余张正常返回、失败张积分退回（流水可查）；
  - VLM 分数与推荐标记正确展示；视觉不可用时优雅降级；
  - `pnpm ci` 全绿 + 手动全流程验证。
- **工作量**：M～L
- **风险**：并行 N 张对 provider 限流的压力——实现时按 provider 能力决定并行度（可退化为串行）。

### 1.5 角色定稿关口

- **现状**：角色参考资产已有 `isCanonical` 语义（`CharacterReferenceAsset`），但无流程约束——
  没有好定妆照的角色照样进入批量出图，锚定错误形象。
- **改动范围**：
  - 复用 `isCanonical` 作为「已定稿」判定（避免加新字段）；
  - 批量出图 / 一键 workflow 启动前检查：存在关联角色未定稿 → 明确提示
    「角色 X 尚未确认定妆照，建议先定稿」，**可跳过不硬阻断**；
  - 角色卡与编辑器角色面板显示定稿状态徽标。
- **验收标准**：未定稿角色批量出图前出现提示且可跳过；定稿后徽标即时更新。
- **工作量**：S

## 5. 阶段二 · 连贯性层（P1）

> 目标：把「连贯性」从 opt-in 的局部机制升级为默认的全链路机制。
> 2.1 为轻方案（允许与阶段一并行），2.2 为治本重方案，2.3 让质检可见。

### 2.1 尾帧衔接智能化（轻方案，可并行先行）

- **现状**：`Scene.videoLinkNext` 为每镜手动布尔开关、默认关；
  `deriveTailFrame`（`use-generation-actions.ts`）取下一镜 imageUrl 做尾帧，
  仅 FL 首尾帧插值路由生效；下一镜未出图时静默回落普通 I2V。
- **改动范围**：
  - **AI 衔接建议**：新增「AI 建议衔接」动作——LLM 批量判断相邻镜对
    「同场景 + 动作连续」→ 返回建议开启的镜头对，一键应用（写 videoLinkNext）；
    解析层（新剧本）可顺带产出该判断，存量项目走按钮触发；
  - **批量生成顺序保障**：批量出视频时按 `order` 串行（runBatch 已串行），
    并在开启衔接的镜头前确保下一镜图已生成（未生成则先出图或提示）；
  - **UI**：分镜卡显示衔接链条状态（已衔接/建议衔接/不适用）。
- **验收标准**：
  - 一键建议后，相邻同场景镜自动开启衔接；
  - 批量视频生成时 FL 路由日志确认尾帧生效；
  - 非 FL 模型静默回落且 UI 有提示（不误导用户以为衔接生效）。
- **工作量**：M

### 2.2 场景锚图（location reference，重方案·治本）

- **现状**：环境每镜由模型独立想象，无共享锚——跨镜背景跳变的根因。
- **改动范围**：
  - **schema**（需 `prisma db push`，服务器部署注意）：
    新表 `ProjectLocation`（id, projectId, name, description, imageUrl）+ `Scene.locationId`；
  - **解析层**：剧本解析时 LLM 聚类「哪些镜头在同一地点」，为每镜标 locationId；
    存量项目提供「AI 识别场景地点」补跑入口；
  - **生成**：每个 location 生成一张环境设定图（无人物，环境+光线+色板），
    用户可重生成/上传替换（复用 1.4 抽卡机制）；
  - **出图注入**：orchestrator 把 location 锚图并入参考图（`reference-composite.ts`
    合成思路扩展，或多图 reference 分槽）。
- **实现要点 / 风险**：
  - ⚠️ **参考图槽位冲突**是已知血泪坑（flow2api 曾把参考图当尾帧，致每段视频结尾闪现立绘，
    靠 planImageInputs 分槽根治）——location 锚图必须走既有分槽机制按 provider 能力注入，
    禁止裸 append 到 referenceImages；
  - 存量项目无 location 数据时行为完全不变（向后兼容）。
- **验收标准**：
  - 同 location 多镜背景一致性肉眼可辨（对比改造前后同剧本出图）；
  - 无 location 数据的旧项目出图行为零回归；
  - schema 变更含迁移说明；`pnpm ci` 全绿。
- **工作量**：L

### 2.3 AI 场记（视觉连贯性体检）

- **现状**：Observer 质检只在自动 workflow 内部跑，手动路径生成完没有任何「AI 审片」；
  用户没有专业眼光，说不出哪里不对（痛点 3 的一半）。
- **改动范围**：
  - 新 API：对项目全部已出图分镜做连贯性检查——VLM 对相邻镜图片对比
    角色服装/发型/环境/光线/色调是否跳变，输出问题清单
    `[{ sceneId, 问题描述, 修复建议 note }]`；
  - 前端「体检」面板：问题清单逐条展示，每条带「按建议重生成」按钮——
    直接走已有的迭代生成机制（iterate + note 提权，`use-generation-actions.ts`）；
  - 复用 Observer Agent 骨架与色板门禁（seriesPalette）作为色调基准。
- **验收标准**：
  - 故意制造一处服装跳变，体检能报出并给出可执行 note；
  - 一键修复走迭代生成且新版本入版本历史；
  - 视觉能力不可用时明确提示（不出假报告）。
- **工作量**：M

## 6. 阶段三 · 全场把控层（P2）

### 3.1 一键 AI 制片人

- **定位**：把阶段一的各点串成一条「一句话 → 完整草稿 → 审阅 → 出图」的流。
- **改动范围**：
  - 编排（大量复用）：1.1 世界观起草 → `DramaScriptAgent` 脚本 →
    脚本→分镜结构化直转（commit 7631d15 已有，零 LLM）→
    `CharacterBibleAgent` 角色建档 + 1.2 外貌预填；
  - **审阅清单页**（新 UI，本项核心增量）：世界观/脚本/每个角色/每镜分镜
    逐项呈现草稿态，用户逐项确认或修改，全部确认后才放行出图（花积分的关口）；
  - 全程仅文本 LLM 调用，出图前有确认关口。
- **验收标准**：新项目从一句话到「待出图完整草稿」零手填可达；每个产物均可修改后再确认。
- **工作量**：M（后端复用度高，主要是审阅 UI）

### 3.2 全片审片报告

- **改动范围**：导出前生成体检报告——时长节奏分布、结尾钩子检查（hookType 已有）、
  连贯性汇总（复用 2.3 结果）、字幕/配音完整性，附修改建议清单。
- **验收标准**：报告可生成、建议条目可跳转到对应分镜。
- **工作量**：S～M

## 7. 排期与依赖

```
批次 1（并行）：1.1 世界观起草 + 1.2 外貌预填 + 1.3 提示词建议   ← 见效最快，治粘贴痛点
批次 2        ：1.4 多候选抽卡+择优 + 1.5 定稿关口              ← 本计划核心
批次 2'（可与批次 1/2 并行）：2.1 尾帧衔接智能化                 ← 轻量连贯先行
批次 3        ：2.2 场景锚图（含 schema 变更）                   ← 连贯性治本
批次 4        ：2.3 AI 场记体检
批次 5        ：3.1 一键 AI 制片人 + 3.2 审片报告
```

依赖关系：1.4 的择优打分器被 2.3 复用；1.2 的预填被 3.1 复用；2.3 的检查被 3.2 复用。
每批次独立可交付、可上线（小步交付原则），遵循 git-first 三步部署流程
（本地 commit + push → 服务器 pull → build + restart + 健康检查）。

## 8. 统一交互设计原则（所有 AI 辅助功能必须遵守）

1. **草稿态标识**：AI 填写的字段带视觉标识，与用户手填区分；
2. **单字段重生成**：不满意某个字段可单独重来，不整表重置；
3. **不覆盖用户修改**：用户改过的字段，AI 再次起草时跳过；
4. **花钱前确认**：所有消耗积分的操作沿用「余额前置 + 成本预览」模式；
5. **降级不阻断**：视觉能力/LLM 配置缺失时功能优雅降级并明示，绝不静默失效或出假结果。

## 10. 有意不做清单（本计划范围外）

- 词级字幕、剪映草稿导出、线索追踪等 backlog 项（见优化 backlog 备忘，另行排期）；
- 硬阻断式的角色定稿门禁（只提示可跳过，避免流程僵化）；
- Seedance 等新 provider 接入（阻塞在外部 API 信息）；
- 实时协同编辑 / 多用户审阅（超出单用户工作流范畴）。
